# Emotorad AI platform — AWS deployment plan (EC2 fast path)

Scope, as decided: **single EC2 instance + Docker, S3, a real domain, CloudWatch logs.** No ECS, no
ALB, no RDS yet — the minimum that gets Phase A (real Bedrock calls, real logging, still-mocked
business tools) live behind a real URL. This replaces the earlier full-architecture draft; ECS
Fargate remains the eventual target (build plan §6) but isn't needed to get something running.

## 0. What has to exist in the code first — this is the actual blocker, not AWS

Right now `src/emotorad_ai` has **no HTTP entrypoint**. `runtime.handle()` is only ever called from
`cli.py`. Before any of the AWS steps below matter, this repo needs:

1. **A thin HTTP wrapper** around `runtime.handle()` (FastAPI or Flask + `uvicorn`/`gunicorn`) that
   accepts an inbound message payload and returns the reply. This is a real, reviewable code change —
   not infra config.
2. **A `/health` endpoint** returning 200, for anything that later checks liveness.
3. **A `Dockerfile`** that installs `requirements.txt` and runs the HTTP wrapper. **Update
   2026-08-24:** `streamlit` moved back into `requirements.txt` — the internal team needs the
   prompt-tuning playground reachable on the deployed box, and the security group (below) allows
   only 443/80 in, so it ships in the same container and `api.py` reverse-proxies `/playground` to
   Streamlit's own server (bound to `127.0.0.1:8501`, not exposed) rather than the playground
   getting its own port. `requirements-dev.txt` is now just local-only tooling on top of the same
   set (currently nothing beyond `requirements.txt` itself).
4. **A `.dockerignore`** (`tests/`, `.git/`, `logs/`, playground files).

None of this exists yet. Say the word and I'll build these four as their own contained, tested unit
before touching AWS — that's the correct order, and it's fast.

## 2. AWS setup, in order

### 2.1 IAM role for the instance

Create an IAM role (instance profile) with:
- `bedrock:InvokeModel` scoped to the **inference profile's ARN** (not a plain foundation-model
  ARN — `ap-south-1` uses Global cross-Region inference, see §1.1) — nothing broader.
- `s3:GetObject`/`s3:PutObject` scoped to the one bucket from step 2.3.
- `logs:CreateLogStream`, `logs:PutLogEvents` scoped to the log group from step 2.5.
- `ssm:GetParameter`/`ssm:GetParameters` for secrets (step 2.4).

No long-lived AWS access keys anywhere in the code or on disk — everything the instance needs comes
through this role.

### 2.2 Security group + instance

- Launch an Amazon Linux 2023 EC2 instance (`t3.small` is enough at pilot volume), in its own
  subnet/security group — not shared with website/checkout compute, per the existing isolation
  decision.
- Security group: inbound **443 only** from the internet (80 too, if using Certbot's HTTP-01
  challenge). **No inbound 22** — use **SSM Session Manager** for shell access instead, which needs
  no open port and no key pair.
- Attach the IAM role from 2.1.
- Elastic IP on the instance, so the domain's A record has a stable target.

### 2.3 S3 bucket

- One bucket for the battery workflow media (diagrams/video that the WhatsApp/chat surfaces fetch).
- Keep it private; serve via signed URLs generated by the app (CloudFront can be added later if
  origin load or caching becomes worth it — not needed to get this live).
- Source assets stay in the repo/PM's Mac for now; only the size-compliant derived copies for
  WhatsApp go to S3 (WhatsApp enforces per-format size limits the raw videos may exceed — re-encoding
  is a content task to do before this bucket has real traffic, not an infra one).

### 2.4 Secrets

- SSM Parameter Store, `SecureString` type, for anything sensitive (WhatsApp tokens later, any API
  keys). Nothing goes into the Docker image or a `.env` file committed to git.
- The container's entrypoint fetches these at startup via the instance role and exports them as env
  vars — `config.py` is already fully env-overridable, so no app code changes needed for this.
- **Playground Basic Auth (added 2026-08-24):** `EMOTORAD_AI_PLAYGROUND_USER` /
  `EMOTORAD_AI_PLAYGROUND_PASSWORD` gate the `/playground` reverse-proxy route (`api.py`) — required
  once the security group is open to the internet on 443 and an internal-only tool sits behind it.
  Currently sourced as GitHub Actions secrets (`PLAYGROUND_BASIC_AUTH_USER`/`_PASSWORD`) and passed
  as plain `-e` flags in `deploy-staging.yml`, **not** yet via the SecureString pattern above — that
  means the value is visible in the SSM command's own parameters to anyone with
  `ssm:GetCommandInvocation` on the account. Acceptable for a first pass; move it into Parameter
  Store (fetched instance-side, never in the command text) if that visibility becomes a problem.

### 2.5 CloudWatch log group

- Create a log group for this service.
- Run the container with `--log-driver=awslogs` pointed at it — Docker ships stdout straight to
  CloudWatch, no separate agent to install.
- `observability.py` already redacts PII before writing its JSONL output — confirm that redaction
  list before this log group carries any real customer conversation (i.e., before R1 traffic, not
  before this pilot setup).

### 2.6 Build and run the container

- Install Docker on the instance via user-data on first boot.
- For a first pass, `docker build` directly on the instance (skip ECR — add it later if/when a CI
  pipeline builds images instead of building by hand).
- `docker run -d --restart unless-stopped --log-driver=awslogs ... <image>` — `--restart
  unless-stopped` is the whole "survives a reboot" story at this scale; no systemd unit needed on top
  of Docker.

### 2.7 Domain

- Point the domain's DNS A record at the instance's Elastic IP (Route 53, or wherever DNS is
  currently hosted).
- TLS: **nginx + Certbot on the instance** is the simplest path for a single EC2 box — nginx
  reverse-proxies to the container's port and Certbot handles the Let's Encrypt cert and renewal.
  (An ALB + ACM cert is the alternative if you'd rather not manage nginx/Certbot yourself, and it
  becomes the ECS target group for free later — but it's an extra service, so leaving it out matches
  what you asked for.)

## 3. What else you'll want to know about, even though it's not "extra setup" today

- **Bedrock access (2.1) is the one step that can silently block everything** — if the model isn't
  approved in `ap-south-1` yet, every real call fails with `AccessDeniedException`. Kick this off
  first, today, independent of everything else.
- **Nothing here talks to real OMS/ERP/Zoho/WhatsApp.** All seven business tools stay mocked (per
  CLAUDE.md: "do not wire real write-access... until the mocked conversational flow has been
  reviewed and tested"). This deployment proves the AWS path — real Bedrock calls, real logs, a real
  URL — not a live customer channel yet.
- **No database yet.** Identity, sessions, and knowledge retrieval are all in-memory/file-based in
  the current code, so nothing here needs RDS. That becomes real at R1 (Langfuse tracing, if you add
  it) and R3 (pgvector) — not part of this pass.
- **No autoscaling, no load balancer.** One instance, one Elastic IP. Fine for a pilot; revisit if/
  when real traffic needs more than one box.
- **Backups**: nothing on this instance is stateful data worth backing up yet (no DB), so this isn't
  a gap today — flag it again once a database exists.
- **Cost alert**: worth a basic CloudWatch billing alarm even at this scale, since Bedrock is
  metered per token and it's easy to not notice a runaway loop until the bill arrives.
